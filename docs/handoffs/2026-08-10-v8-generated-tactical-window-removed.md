# V8 Generated-Tactical Window — removed from live play 2026-08-10

Branch: `claude/generated-tactical-window-6dxfay`

## Decision

Owner direction: "Tactical cards should be generated by playing a player, and then they can be
used on subsequent turns. It's simple." The post-reveal, same-period Generated-Tactical Window is
removed from both live gameplay paths. A Tactical generated this period is **never** playable this
period, in any period including P4 — it becomes selectable through the following period's ordinary
commitment phase, exactly like every other held card.

This does **not** touch card content, Actions, or the window's API surface. See "What was and
wasn't touched" below.

## What changed

**`src/engine-v8/calibration-matchup-matrix.ts`** — `simulateV8CalibrationMatch` no longer calls
`planV8CalibrationWindow` / `resolveGeneratedTacticalWindow` after reveal resolution. It goes
straight from `resolveSequence` to reading zone totals and scoring. `planV8CalibrationWindow` the
function is untouched (see below) and its import removed only where it was calling
`resolveGeneratedTacticalWindow`.

**`src/components/match-v8/V8CalibrationLab.tsx`** — the entire `windowPhase` interactive step
is removed: the `WindowPhase` type, its `useState`, `queueWindowPlay`/`unqueueWindowPlay`/
`resolveWindow`, the `windowChoices`/`windowRemainingEnergy` memo, the `v8-window` JSX branch, and
every `windowPhase ? … : …` conditional threaded through `isHandDragZoneLegal`, `queueTacticalToZone`,
`queueToZone`, hand-card affordability, the drag ghost, and the zone guide text. `endPeriod` now
always calls `finishPeriod` directly — one click, reveal straight through to scoring, same as every
other period transition.

`TacticalHandCard` lost its `fresh` prop (it existed only to glow a Tactical that was playable
*this* period via the window — that state no longer exists). A generated-but-not-yet-available
Tactical instead falls into the same `is-unaffordable` dimming that unaffordable players already
use, driven by `isCalibrationTacticalAvailable`. In practice this dimming is never visibly
reachable through this Lab's own reveal flow, because reveal and period-advance happen in the same
state update — by the time a generated card appears in the human's hand, `availableFromPeriod` has
already caught up to the new `state.period`. The gating is kept anyway as the correct invariant,
not dead code: it is what actually enforces "not this period" for cards from other generation paths
(CPU planner side, future non-reveal sources) even though the interactive Lab's own timeline never
exercises the dimmed state.

**`src/components/match-v8/v8lab.css`** — removed the now-dead `.v8-window`, `.v8-window__choices`,
`.v8-window__remove` rules (three locations: base, mobile breakpoint, "exception" override) and the
`.v8-card--chance.is-fresh` / `v8-window-arrive` / `v8-tactical-arrive` animation rules, plus their
listing in the `prefers-reduced-motion` block. `.v8-chip.is-fresh` (the *player*-reveal glow) is
unrelated and kept.

**`tests/v8-match-lab.spec.ts`** — the three window-specific tests are replaced with two tests
that assert the corrected contract: generating a Tactical never opens `[data-testid="v8-window"]`
and the period scores in one click; the same Tactical shows up in hand at the start of the
following period, not dimmed, and is playable there via the ordinary drag-to-commit flow. All 10
V8 lab Playwright tests pass at 390×844.

**Tracked matrix evidence** (`test-results/v8-calibration-matrix.{json,txt}`,
`v8-calibration-periods.{json,txt}`, `v8-calibration-scoring-sensitivity.{json,txt}`) — regenerated
against the corrected simulator. Window plays now read `0 plays / 0 E / 0 ATT` for every squad, and
win rates shift accordingly: Long Shot / Set Piece falls from 38% to 25% (it depended most heavily
on same-period window play), Cross falls from 51% to 49%, Dribbling/Penalty rises from 33% to 54%.
These numbers are the honest post-fix baseline, not a tuning pass — no card values changed.

## What was and wasn't touched

**Not touched, deliberately:**

- Every card definition, Action, and generation effect across the original 30 cards and the
  Batch 01–07 expansion (~45+ cards). They still call `addCalibrationTacticalToHand` /
  `generateTacticalMutable` exactly as before; `availableFromPeriod = generatedPeriod + 1` was
  already being set unconditionally at generation time by every one of these call sites (confirmed
  by reading `calibration-decay.ts`'s `holdRevealGeneratedTacticals` and every Batch 05/07 reveal
  effect in `calibration-engine.ts`). Removing the window's *invocation* was sufficient — no
  generation-site code needed to change for the new rule to hold everywhere.
- The 8 independent `resolveGeneratedTacticalWindow` definitions (base + 7 layered batch wrappers)
  and the window API surface (`planV8CalibrationWindow`, `windowEligibleCalibrationTacticals`,
  `V8CalibrationWindowPlay`, the four `window*` telemetry fields, `enteredHandPeriod`). These
  remain live code, still exported from `index.ts`, and are still exercised by roughly a dozen
  isolated sensitivity/balance harness files (`calibration-dribbling-*.ts`,
  `calibration-cross-minimal.ts`, `calibration-compact-core.ts`, `calibration-deck-validation.ts`)
  that call them directly in their own hand-rolled match sequences, separate from the live matchup
  matrix. Deleting the API would have broken compilation of all of those files and their tests for
  no behavioral gain, since they're isolated evidence-gathering tools, not the live game.
- `calibration-window-planner.test.ts`, `generated-tactical-window.test.ts`, and every
  Batch-0X-window test — all still pass unchanged, because they test the API directly rather than
  through the two call sites that were removed.

**The net effect:** the live game (the matchup matrix used for balance evidence, and the
interactive Lab a human actually plays) now enforces "generate this period, play next period" with
zero same-period exception, while the window mechanism itself survives as inert, still-tested
library code that the isolated harnesses can keep using for whatever they're measuring.

## Why not a full revert

The owner's first message asked to revert the whole Generated-Tactical Window spec. Before acting,
inventory of the branch found 335 commits (43 directly touching the window) built on top of it in
the ~36 hours since it was introduced: planner sequencing intelligence, balance sensitivity sweeps,
and Batch 02–07 card integration, plus a substantial mobile drag-and-drop UI pass. A blind revert
would have discarded or broken that work. The owner's follow-up clarified the actual requirement —
no same-period play, full stop — which this change delivers as a two-call-site removal plus a
UI simplification, leaving all downstream card content and tooling intact.
